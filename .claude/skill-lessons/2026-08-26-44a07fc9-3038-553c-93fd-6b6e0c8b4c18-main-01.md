# .claude/agents/investigator.md — query the external dependency directly before the VM when a setup step died on a fetch

- Added: 2026-08-26
- Evidence: An FB Tests job (podman `@user-password`) died in `Run Setup for E2E Tests` while building the PSMDB replica-set image; the log showed `dnf` taking 404s on two named `pmm3-client-experimental` repodata files. A single unauthenticated fetch of that repo's current `repomd.xml` — before any VM existed — showed it referencing a different, fully resolvable set of hashes while the two hashes from the log still 404'd, and the package timestamps inside `primary.xml.gz` dated the newly published client build to 08:55 UTC with the repodata regenerated at 08:58, 14 minutes before the job's 09:12 `dnf` run. That named the mechanism (a repo publish / mirror-sync race, external to PMM and to the PR) and predicted the outcome of the reproduction, which then only had to confirm it: the identical `docker compose build --no-cache` succeeded twice on the throwaway VM.
- Proposed change: In the Reproduce step, add that when the failing step is an external fetch — a 404/403/timeout on a package repo, container registry, or artifact URL named in the log — first query that URL's current state directly and compare it against the exact identifiers the log requested, then still reproduce on the VM. The pre-check costs one request, names the mechanism, and tells you whether the repro is expected to reproduce; it is what turns a bare "flake" verdict into a dated root cause the PR comment can stand on.
