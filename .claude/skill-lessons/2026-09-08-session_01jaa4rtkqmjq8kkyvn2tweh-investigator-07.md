# .claude/agents/investigator.md — a package-repo publish race and a slow mirror look alike in a log; the mismatch is the tell, and the index's own timestamp is a load-independent probe

- Added: 2026-09-08
- Applies to: target only
- Evidence: five failures across four OSes and both arches were initially candidates for the run's own 50-way concurrency, but each carried a *mismatch* rather than a timeout — `File has unexpected size (1171 != 1172). Mirror sync in progress?`, `Status code: 404 for .../repodata/<hash>-primary.xml.gz`, `Server reports Content-Length: 87651948 but expected size is: 87652000` — i.e. the repo changing under the client, not a slow transfer (which shows as exit 124 and partial byte counts). Re-fetching the repo's own `Release` during triage gave `Date: …14:52:12` against the failing log's `Release file created at: …13:52:29`, showing an hourly regeneration at ~:52; all five failures fell in 13:50-14:06.
- Proposed change: in the external-fetch paragraph, add that a hash/size/`Content-Length` mismatch or a 404 on a repodata file the just-fetched `repomd.xml` named is a publish race and not bandwidth, and that unlike a throughput probe (which cannot speak to the busy window) a re-fetch of the index's own generation timestamp is load-independent and can be compared against the failing log directly; note that failures scattered across OSes but clustered in time implicate the shared external dependency rather than the suites.
