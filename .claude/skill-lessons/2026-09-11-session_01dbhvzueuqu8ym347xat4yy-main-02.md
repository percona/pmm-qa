# .claude/skills/repos/SKILL.md — a CI script that clones into a temp dir must authenticate its push explicitly; the checkout's token does not carry over

- Added: 2026-09-11
- Applies to: all skills that push to GitHub from CI via a secondary clone (publishing to gh-pages, cross-branch data commits)
- Evidence: A publish script read `remote.origin.url` and `git clone`d it into a `mktemp -d` to commit and push a report. `actions/checkout` persists its token only into the *workspace* repo's local `.git/config` (`http.<host>.extraheader`), which a fresh clone never inherits, so the push would have run unauthenticated and failed with 403 regardless of `permissions: contents: write` — and only on the last line, after the clone and commit. A reviewer caught it before a first run. A second, related finding: two concurrent publishes to the shared branch race, and the loser's non-fast-forward rejection under `set -e` dropped the run.
- Proposed change: When a CI script pushes from a clone it made itself, build the remote explicitly — `PAGES_REMOTE`, else `https://x-access-token:${GITHUB_TOKEN}@github.com/${GITHUB_REPOSITORY}.git` — and fail loud *before* cloning when neither is set in CI (`GITHUB_ACTIONS`), keeping the `origin` fallback only outside CI. Wrap the commit-and-push in a bounded fetch → `reset --hard origin/<branch>` → rebuild → retry loop so parallel jobs don't lose a run.
