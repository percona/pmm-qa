# .claude/skills/fb-tests/SKILL.md — list_workflow_jobs already carries steps and always spills; parse the spill, don't re-fetch per job

- Added: 2026-09-11
- Applies to: target only
- Evidence: Surveying the ps-integration job across 10 FB Tests runs, every `actions_list` → `list_workflow_jobs` call spilled to a file (213-215 KB each; the FB matrix has ~100 jobs and the payload embeds each job's full `steps` array with `conclusion`, `started_at`, `completed_at`). Those embedded steps answered the whole question, so the per-job `actions_get` → `get_workflow_job` that SKILL.md line 25 prescribes for "step-level conclusions" was never needed. The spill note's advice to read the file in 80k-char spans would have pushed ~2 MB into context for 10 runs; four parallel calls plus one reusable python3 parser over the spilled paths cost a few hundred tokens instead.
- Proposed change: In the run/attempt triage paragraph, note that `list_workflow_jobs` returns each job's full `steps` array (so `get_workflow_job` is only needed when a job listing is unavailable), warn that the call reliably spills to a file with the nested shape `{"jobs": {"total_count": N, "jobs": [...]}}` unlike the flat `list_workflow_runs` response, and direct the reader to batch the calls in parallel and filter the spilled JSON with a small script rather than reading the file in character spans.
