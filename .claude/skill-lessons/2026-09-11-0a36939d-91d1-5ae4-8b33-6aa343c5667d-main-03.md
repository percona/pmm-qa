# .claude/skills/fb-tests/SKILL.md — separate slow-network from slow-work by comparing per-download rates, not step totals

- Added: 2026-09-11
- Applies to: target only
- Evidence: Aggregated step timings made a 57 min setup look like uniform slowness, and the first two hypotheses drawn from them (mirror throttling, then a fixed per-connection penalty) were both wrong. The answer was in the logs' own `Fetched <size> in <time> (<rate>)` lines: the same 32.6 MB index ran at 7.9-13.2 MB/s in a fast run and 1.2 MB/s decaying to 44.1 kB/s in a slow one, and `repo.percona.com` degraded alongside `archive.ubuntu.com`, ruling out a single-mirror throttle. Two jobs in the *same* run differing 7m23s vs 50 min, and a re-run of the slow one at 2m27s, then pinned it to the individual runner VM.
- Proposed change: In the artifact/log-reading section, note that for a job that is slow rather than failed, grep the apt/wget `Fetched ... (<rate>)` lines and compare rates against a known-fast run of the same job; more than one external host degrading together rules out a mirror-side throttle, and comparing two jobs inside one run (or re-running the slow one) distinguishes a per-VM network problem from a time-of-day or repo-wide one.
