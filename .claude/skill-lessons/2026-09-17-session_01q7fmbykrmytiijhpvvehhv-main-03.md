# .claude/skills/linode-docker-provisioning/SKILL.md — a second single-node `mysql=` framework run destroys the first instance's /tmp mount

- Added: 2026-09-17
- Applies to: .claude/skills/linode-docker-provisioning/SKILL.md
- Evidence: Adding a second MySQL instance to a box that already had one (`--database mysql=8.4` alongside a live `mysql_pmm_8_0_1`) silently broke the first. The mysql playbook's "Prepare socket folders" task `rm -rf`s `/tmp/mysql-sockets/<node-index>`, keyed on node index only and not on version, and the running container bind-mounts that exact path as its `/tmp`. Monitoring stayed green (`mysql_up=1`, the exporter uses 127.0.0.1:3306) so the damage was invisible in PMM, but the container's `/tmp` became a deleted directory. `systemctl restart mysql` inside it then failed outright — InnoDB `Unable to create temporary file inside "/tmp"; errno: 2` — turning a broken CLI socket into a down server. `docker restart` was not the recovery either: it re-resolves the bind onto the live directory the new instance now owns, putting two servers on one `/tmp/mysql.sock`. The fix was to move the first instance off the dead mount in its own `my.cnf` (`socket=`, `mysqlx_socket=`, `tmpdir=` under a normal in-container directory) and restart mysqld in place. The PS playbook does not use that shared path, so `ps=` runs never collided.
- Proposed change: In the databases step, warn that a second `--database mysql=<ver>` run on a box that already has a single-node MySQL wipes `/tmp/mysql-sockets/1` out from under the existing container, and that a green `mysql_up` does not clear it; add a second instance as `ps=` or a different database type where possible, and if a MySQL one is required, recover by repointing the older container's `socket`/`mysqlx_socket`/`tmpdir` off `/tmp` and restarting mysqld inside the container — never `docker restart` it, which collides both servers on one socket path.
