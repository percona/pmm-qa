# .claude/agents/investigator.md — the run-logs zip already splits each job into per-step files

- Added: 2026-09-18
- Applies to: .claude/agents/investigator.md (the "CI trigger payload" bullet's run-logs-zip recipe)
- Evidence: The bullet describes the zip as "one `<n>_<job name>.txt` per job carrying every step's output" located with `grep -n '##\[group\]'`. The zip for an FB Tests run actually holds both that flat file **and** a per-job directory of per-step files named `<job name>/<step number>_<step name>.txt`, so the failing step is opened directly — `actions_get`→`get_workflow_job` already names it and its number. In the same run a `get_job_logs` tail of 120 lines landed wholly past the failing step (it ran 16:40:07-16:40:10; the window opened at 16:40:10) and showed none of the error. Extraction also needs `unzip -q -o`: the flat `<job>.txt` and the per-job directory collide on entries such as `system.txt`, and with no tty the overwrite prompt reads EOF, prints `(EOF or read error, treating as "[N]one" ...)` and silently leaves files missing, which reads as a truncated zip.
- Proposed change: Correct the bullet to say the zip unpacks a per-job directory of `<step number>_<step name>.txt` files, that the failing step's number and name come from `get_workflow_job` so the exact file is known before opening anything, and that extraction uses `unzip -q -o` because the flat and per-directory entries collide.
