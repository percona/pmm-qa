# .claude/skills/codeceptjs-migration/branch-workflow.md — a single-VM Run job cannot reproduce the nightly's multi-shard topology

- Added: 2026-10-19
- Applies to: branch-workflow.md Attach CI execution, for tests that count nodes or services spread across nightly shards
- Evidence: Row 39 PMM-T68 asserts 2 `ProxySQL Instance` options. Nightly gets 2 because `nightly-e2e-tests-matrix.yml` runs `--database pxc` on two shards (`ps-gr-pxc-valkey`, `extra-pxc-pdpgsql-haproxy`), each registering `pxc_proxysql_pmm_8_4-$SHARD_NAME` with the shared server. The dispatched runner job (one VM) had 1 and failed T68 on all 3 attempts while 15/16 passed. A second PXC on one VM was blocked only by `images/pxc-proxysql/setup.sh` publishing host port 6033 (unused by any test; the old Ansible framework had the same `-p 6033:6033`). Dropping it (6f30b825, on the PR at Kiran's request) let `--database pxc --database pxc=8.0` give 2 nodes; T68 passed locally. CodeRabbit raised the 1-ProxySQL point twice and withdrew both after the shard evidence.
- Proposed change: In Attach CI execution, say: before calling a Run-job failure environment-only, find what the nightly topology supplies (count the shards providing it) and what stops one VM from supplying it; a fixed host port or container name in pmm-framework is a framework fix in the same PR, verified with the pmm-framework-change skill, then add the extra database to the dispatch's `setup_services`.
