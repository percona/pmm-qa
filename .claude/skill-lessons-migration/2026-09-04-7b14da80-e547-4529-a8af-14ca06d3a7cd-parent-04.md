# .claude/skills/codeceptjs-migration/locator-fix.md — two ways an MCP locator check silently answers the wrong question

- Added: 2026-09-04
- Applies to: `.claude/skills/codeceptjs-migration/locator-fix.md`
- Evidence: Row 5, both found while verifying an iframe-scoping fix on `graph/admin/settings`.
  1. Navigating MCP to a URL carrying basic-auth credentials (`https://admin:admin@127.0.0.1/graph/admin/settings`) bypasses the PMM shell entirely: Grafana renders at top level, `#grafana-iframe` is absent, and the settings table never mounts. A reviewer checking iframe-scoped locators that way would confidently conclude that a correct iframe fix is wrong. A clean navigation reproduces the redirect to `/pmm-ui/graph/admin/settings` and the iframe.
  2. `@playwright/test`'s `expect` is not loadable inside the Playwright MCP server process — `require` of both `@playwright/test` and `playwright/test` failed — so a literal `toHaveText` mutation proof cannot be run there. Emulating it with strict single-node resolution plus whitespace-normalized `textContent` equality is faithful, but has to be declared as an emulation rather than reported as a bare PASS/FAIL. Attempt 1 of the initial gate reported PASS/FAIL without the caveat; attempt 2 surfaced it.
- Proposed change: Add both to `locator-fix.md`. For the second, also record the stronger form: when narrowing an ambiguous locator, compare the un-narrowed locator's `allTextContents()` against the narrowed one's. On row 5 that returned `["postgres","database"]` versus a single `postgres`, which names the node the narrowing dropped — a mutation PASS/FAIL only shows that some assertion moved, not which element it stopped matching.
