# .claude/skills/codeceptjs-migration/branch-workflow.md - edit a tracked file byte-level on Windows, never through a text-mode read/write round trip

- Added: 2026-09-15
- Applies to: `.claude/skills/codeceptjs-migration/branch-workflow.md` ("Control branch preflight"), and every step that edits `tracker.md`
- Evidence: Row 10's `pending -> in-progress` commit was a one-cell change, and `git show --stat` reported `164 insertions(+), 164 deletions(-)`. `tracker.md` is LF-only; Python's `Path.read_text()` translates `\r\n` to `\n` on read and `Path.write_text()` translates `\n` back to `os.linesep` on write, so on Windows the round trip rewrote every line of the file to CRLF. The diff was byte-noise around one real change, and nothing in the commit output says "line endings" - the only tell is the insertion count. `git checkout HEAD~1 -- tracker.md`, a `read_bytes`/`replace`/`write_bytes` redo, and `--amend` produced the intended `1 insertion(+), 1 deletion(-)`. The same defect would have reached the PR had it landed on a publish-branch file instead of a control-only one.
- Proposed change: In that section, state that any scripted edit to a tracked file is byte-level (`open(...,'rb')` / `replace` / `open(...,'wb')`, or the repo's own `sed` forms), never `read_text`/`write_text`, and that the edit is verified with `git diff --numstat` before staging - a one-cell change reads `1 1`. Give the failing form explicitly so it is recognised rather than re-derived.
