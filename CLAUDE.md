## House style (applies to every session, agent, and routine)

This section is the single global lever for cross-cutting preferences — it loads in every session, including multi-repo ones where the project `.claude/settings.json` does not. To change how all of PMM AI writes code or behaves, edit **here**, not each agent/routine file.

- **Minimal comments.** Write code that reads like the surrounding file. Only comment the non-obvious — a tricky invariant, a workaround with a reason, a public API contract. Do not narrate what the code plainly says, and do not add header/section banners. Match the comment density already present in the file you are editing. **A fix that came out of a long investigation is where this rule breaks**: the mechanism, version history and measured numbers feel like they belong beside the code, and they do not — that is a decision record for the PR body. One two-file fix drew a reviewer finding on each file, both citing this rule. The file comment keeps only what a reader at that line cannot infer from the code beside it.
- **Reach for the helper the file already has.** Before adding a function, grep the file for one that already does the work — a 30-line bespoke scroller was rejected ("temos o loadAllPanels que supostamente faz isso, nao?") and calling the existing helper made the block smaller than the code it replaced. The converse holds too: when a change only makes existing **inline** code do more, keep it inline. Hoisting a widened inline block into a named helper with exactly one caller drew "Pra que criar esse metodo se antes estava inlined?" and was inlined back unchanged. A new named helper needs a second caller, or a file that already factors that shape out.
- **A grep hit proves a string exists, not that it is on the path under investigation.** Trace producer to consumer and name the call site that reads the value before asserting a mechanism. Three root-cause claims in one session were asserted from a grep and refuted: a dashboard variable's `role!="sentinel"` filter (the playbook labels those services `role=primary`/`role=replica`), a `[PDPGSQL_PGSM_CONTAINER]=` assignment in a setup file the consuming playbook never runs, and a stale `itemCount` where the defect was the unit of iteration. Each cost a wrong statement to the user.
- **Read a value from its source in the same turn you quote it.** Any credential, URL, IP, host or version reported to the user comes from a read performed in that turn — never report and verify afterwards. A provisioning summary stated an admin password that had never been read from `provision.json`; the real value arrived on the next call and forced a correction.
- **A local tooling workaround never mutates a tracked file.** Copy it to the scratch directory, patch the copy, and point the tool at it (`--config`, `--project`, …) — editing a tracked lint or build config in place changes what everyone else runs. When the config resolves paths **relatively** (`./codeceptConfigHelper`, `./tests/helper/hooks.js`), a scratch-directory copy cannot load: put the patched copy beside the original under an untracked name and pass it with the tool's own config flag. Either way the tracked file stays untouched.
- **Address a directory by its literal absolute path.** `cd "$VAR"` guarded only by `||` is forbidden: an unset variable makes `cd ""` a successful no-op, so the fallback never runs and the command executes in whatever directory the harness reset to — that is how `npm init` and downloaded CI artifacts landed in the tracked checkout. `mkdir -p` an absolute scratch subdir and `cd <literal path> || exit 1`, confirming `pwd`, before any file-creating or package-manager command. **Batched or parallel Bash calls share one working directory**, so a leading `cd <repo> &&` in one call moves the ground under the others: two calls issued in the same response each opened with `cd /workspace/<repo> && git show …` and the second failed with "Not a valid object name origin/main". Use `git -C /workspace/<repo> …` and absolute file paths instead of a leading `cd`.
- **Capture a command's own exit status; never read it through a pipe.** `out=$(cmd 2>&1); rc=$?`, then branch on `$rc`. A retry loop written as `if git push … 2>&1 | tail -3; then break; fi` tests `tail`, which exits 0 on the first failure and reports a push that never landed; `cmd | head -4; echo "rc=$?"` measures `head` the same way.
- **A scripted multi-line replacement anchors on unique start and end strings**, asserting each is present and unambiguous — never on a `sed -n 'A,Bp'` line-range snapshot, which ends mid-block and leaves a duplicated tail. Run the file's own syntax check (`bash -n`, `node --check`, …) immediately afterwards.
- **Read a third-party action's or library's own inputs before hand-rolling behaviour inside it.** Retry, pagination, auth, logging and timeout are usually already parameters — `actions/github-script` takes `retries`, which collapsed a 93-line hand-written backoff into one line per step. For a pinned ref, `curl raw.githubusercontent.com/<owner>/<repo>/<ref>/action.yml` reads them without guessing.
- **Re-read a copied comment against the file it lands in.** The same block applied to three files carried one justification that was true in one of them and plainly false in the other two. A comment rewritten in response to review gets re-checked for the same defect, not reworded around it.
- **Kill by pid, not by pattern.** `pkill -f <pattern>` matches your own command line, so it kills the calling shell and takes the rest of the compound command with it. `pgrep` first, then `kill -9 <pid>`.
- **Never run a `.claude/hooks/` hook by hand as a check.** The harness invokes it with a JSON payload on stdin, so a manual run reads `/dev/null`, reports success having linted nothing, or hangs on stdin. Call the underlying tool instead (`.claude/hooks/lint-changed.sh <files>`) and let the gate fire on `git commit`. A file belongs under `.claude/hooks/` only when `.claude/settings.json` wires it to a hook event; every other script goes under `.claude/scripts/`.
- **A green `Lint` check does not mean your diff was linted.** `lint-changed.sh` dispatches by extension and then skips any workspace whose `package.json` has no `"lint"` script — `codeceptjs-e2e` has none, so a `.js`-only diff there passes the gate unlinted while `Lint` goes green off other files. Markdown has no group at all. Before citing a green gate, confirm the dispatcher actually selected the changed files; when it did not, say "no gate covers these files" and name what you ran instead (`node --check`, `bash -n`).
- **While a merge or rebase is in progress, stage the resolved paths by name.** `git add -A` cannot tell a conflict resolution from unrelated work already in the tree: it once swept new tests written earlier in the same turn into a merge commit, whose message then had to be amended to cover them. Check `git diff --diff-filter=U --name-only` and `git add <path>…`.
- **Poll a harness background task on its exit marker**, `[exited with code`, as well as on any content string — and prefer the completion notification the harness delivers on its own to an interval poll of the output file. A loop matching only content ran twenty 30-second iterations after the work had already finished.
